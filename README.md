# Task 3 — Persistent Data Layer

Innovation Hacks Full Stack Development Internship.
Upgrades the Task 2 API from SQLite to a real, persistent **PostgreSQL** database using
**Prisma ORM** — proper migrations, a typed schema, and connection pooling instead of a single
local file.

## ⚠️ Note on testing

This was built without a live Postgres connection or network access in the sandbox it was
written in, so it hasn't been run end-to-end yet. Every file passed `node --check` (valid JS)
and the Prisma schema was reviewed carefully, but **you need to connect a real database and
run the migration before this will actually work** — see Step 2 below. If anything errors,
paste it to me and I'll fix it.

## Why Postgres + Prisma over the Task 2 setup

| | Task 2 (SQLite) | Task 3 (Postgres + Prisma) |
|---|---|---|
| Storage | Single local file | Real hosted database server |
| Survives redeploys | ❌ (resets on free hosts like Render) | ✅ |
| Concurrent writes | Limited | Handled properly |
| Schema changes | Manual SQL | Tracked migrations (`prisma migrate`) |
| Query safety | Raw SQL strings | Type-checked queries |

## 1. Get a free Postgres database

Pick one (both have generous free tiers, no credit card needed):
- **Neon** — neon.tech → sign up → "Create a project" → copy the connection string
- **Supabase** — supabase.com → new project → Settings → Database → copy the connection string

You'll get a URL like:
```
postgresql://user:password@host/dbname?sslmode=require
```

## 2. Set up and run

```bash
cd task3-persistent-data-layer
cp .env.example .env
# paste your DATABASE_URL and set a JWT_SECRET in .env

npm install
npx prisma migrate dev --name init   # creates the tables
npm run seed                          # optional: adds sample users/project/tasks
npm start
```

Server starts on `http://localhost:4000`.

If you ran the seed script, you can log in immediately with:
- `ada@example.com` / `secret123`
- `grace@example.com` / `secret123`

## 3. Explore your data visually

```bash
npx prisma studio
```
Opens a browser-based table editor for your database — handy for checking the seed data landed correctly, or debugging without writing SQL.

## 4. What changed from Task 2

The REST API surface (routes, request/response shapes, status codes, permission rules) is
**identical to Task 2** — this task is purely about the data layer underneath:

- `db/index.js` (raw SQLite) → `db.js` (Prisma client singleton)
- Hand-written SQL (`db.prepare(...)`) → Prisma queries (`prisma.task.findMany(...)`)
- No migration history → `prisma/schema.prisma` + tracked migrations in `prisma/migrations/`
- Manual foreign key checks → enforced at the database level via Prisma relations
- No seed data → `prisma/seed.js` for repeatable sample data

## 6. Deploying this version

Same as Task 2 (Render), with one addition: set `DATABASE_URL` as an environment variable in
Render's dashboard (pointing at your Neon/Supabase database), and add this as your **Build
Command** so migrations run automatically on deploy:
```
npm install && npx prisma migrate deploy && npx prisma generate
```

## 7. What I'd extend first

1. **Connection pooling for serverless** — if you later deploy to a serverless platform (Vercel,
   AWS Lambda), add Prisma's connection pooling (`pgbouncer=true` in the URL) since serverless
   functions can exhaust direct Postgres connections quickly.
2. **Soft deletes** — right now `DELETE` permanently removes rows; an `deletedAt` timestamp
   column would let you "undo" deletions.
3. **Indexes on `status` and `dueDate`** — useful once task lists grow large and get filtered/sorted often.
4. **Transactions** — e.g. wrap task creation + notification logic in `prisma.$transaction([...])`
   once Task 4 adds more side effects per action.
